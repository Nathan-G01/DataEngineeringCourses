# Secure data access in Microsoft Fabric

## Introduction  

**Security in Microsoft Fabric** is designed to **control data access** based on user roles and responsibilities. It enables **granular access control** through **workspace permissions, item-level permissions, compute permissions, and OneLake data access roles (Preview)**.  

### **Use Case-Based Security Approach:**  
- **Data Engineers** – Need **lakehouse access** to develop **data products**.  
- **Analysts** – Query data for **business insights**.  
- **Data Scientists** – Use **Apache Spark** for modeling and experiments.  
- **Report Creators** – Build **Power BI reports** for distribution.  
- **Report Consumers** – View **reports** to make decisions.  

### **Fabric’s Multi-Layer Security Model:**  
- **Workspace-level security** – Restrict access at the **workspace** level.  
- **Item-level permissions** – Grant access to **specific data objects**.  
- **Granular security** – Apply **row-, column-, or role-based permissions**.  

By mastering Fabric’s security model, you can **protect sensitive data** while ensuring users have the **necessary access** for their roles.

## Understand the Fabric Security Model  

**Microsoft Fabric** provides a **multi-layer security model** to control **data access** based on **user roles, responsibilities, and organizational deployment patterns**. It follows the **principle of least privilege**, ensuring users have only the necessary permissions.  

### **Three Security Levels (Evaluated Sequentially):**  
1. **Microsoft Entra ID Authentication** – Verifies user identity.  
2. **Fabric Access Control** – Determines if the user can access Fabric.  
3. **Data Security** – Checks if the user has **specific permissions** for the requested action.  

### **Fabric Security Building Blocks:**  
- **Workspace Roles** – Control access at the **workspace level**.  
- **Item Permissions** – Override workspace roles for **specific data items** (e.g., lakehouses, warehouses).  
- **Granular Permissions** – Apply fine-grained access like **Read, ReadData, or ReadAll**.  
- **Compute Permissions** – Manage access to **specific compute engines** (e.g., SQL Endpoint, semantic models).  
- **OneLake Data Access (Preview)** – **Restricts folder or file-level access** in a lakehouse using **RBAC**.  

This layered security model ensures **flexible, role-based data access**, preventing unauthorized actions while maintaining **efficient data governance**.

## Configure Workspace and Item Permissions  

**Workspaces** in **Microsoft Fabric** allow users to collaborate by managing **Fabric items** such as **lakehouses, warehouses, and reports**. **Workspace roles** define what users can **view, modify, and manage**, while **item permissions** provide **fine-grained access control** for specific items.  

### **Workspace Roles:**  
Users can be assigned one of four **workspace roles**, which apply to **all items** in the workspace:  
- **Admin** – Full control, including permissions management.  
- **Member** – Can modify and share content.  
- **Contributor** – Can modify content but cannot share.  
- **Viewer** – Can only view content without modification.  

### **Assigning Workspace Roles:**  
- Navigate to the **Manage access** option in the workspace.  
- Add the user and select their role.  

### **Configuring Item Permissions:**  
When a user **no longer needs full workspace access**, you can restrict their permissions to **specific Fabric items** using **item-level permissions**.  

For example:  
- A **data engineer** initially had **Contributor** access but later only needs **read access** to a **lakehouse**.  
- The **Contributor role is removed**, and **item-level permissions** are assigned to allow access **only to the lakehouse**.  
- To grant access to **data** and not just **metadata**, select **Read all SQL endpoint data** or **Read all Apache Spark**.  

### **Best Practices:**  
- Use **workspace roles** for broad access control.  
- Use **item permissions** for **least privilege access** when users only need specific items.  
- Each **Fabric data item** has its own **security model**, so configure permissions accordingly for **warehouses, lakehouses, and semantic models**.

## Apply Granular Permissions  

When **workspace roles** and **item permissions** are insufficient, **granular permissions** can be applied through:  
- **SQL analytics endpoint** (for Lakehouses & Warehouses)  
- **OneLake data access roles (Preview)** (for folder-level security)  
- **Warehouse permissions**  
- **Semantic model security**  

### **Lakehouse Granular Permissions via SQL Analytics Endpoint:**  
- Each **lakehouse** has an **autogenerated SQL analytics endpoint** to manage data security.  
- **T-SQL commands (GRANT, DENY, REVOKE)** can restrict access to SQL objects.  
- **Supports Row-Level Security (RLS), Column-Level Security (CLS), and Dynamic Data Masking (DDM).**  

### **OneLake Data Access Roles (Preview):**  
- **Fine-tune folder-level security** beyond workspace permissions.  
- Create **custom roles** and assign them **read access to specific folders**.  
- Folder security **inherits permissions** across subfolders.  

### **Granular Warehouse Permissions:**  
- Uses the **SQL analytics endpoint** for **T-SQL-based access control**.  
- Supports **GRANT, REVOKE, DENY**, and **security policies** (RLS, CLS, DDM).  

### **Semantic Model Permissions:**  
- **Workspace roles control default access** to semantic models.  
- **Row-Level Security (RLS)** in Power BI allows **fine-grained access control** via **DAX security rules**.  

### **Best Practices:**  
- Use **SQL analytics endpoint** for structured **database object permissions**.  
- Apply **OneLake data access roles** for **file and folder security**.  
- Secure **semantic models** with **Power BI RLS** for report-specific data protection.
